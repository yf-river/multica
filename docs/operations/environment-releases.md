# 任务交付与固定环境发布

本流程用于需要验证、发布 Multica 程序的任务。咨询、调查、文档等普通任务使用现有任务状态与评论，其他项目按各自规则处理；不因 Agent 名称或任务所在平台自动登记交付。

未启用项目发布 Agent 的交付沿用本页原有的单项授权和发布流程。配置并启用发布 Agent 的项目使用下述项目流程；生产批准、代码提交、测试证据和实际运行版本分别保存，不能相互代替。

## 发布 Agent 管理的项目

在任务看板的待发布列配置发布 Agent 和项目。任务负责人在独立分支登记准确提交与业务检查，提交审核；审核通过后进入进行中并分配空闲的 verify 槽位。verify 前端从任务工作目录运行开发服务，后端按固定提交构建；测试中修复须登记新提交，在原槽位更新并重新审查。审查、任务测试和最终组合联调分别对应三个对勾，提交或候选变化时旧结果失效。

测试完成的任务进入待发布。发布器按第一项等待时间收集 10 分钟，冻结成员与各自提交；只允许一批占用 int 和生产发布通道。合并冲突保留批次，修复代码须重新审查和测试。发布器基于最新主分支生成组合候选并构建一次，int 对固定候选进行共同检查和必要的成员联调；各成员按自身检查清单提交证据。无独立联调项的任务需记录原因，组合仍须完成基本业务检查。通过后同一制品应用到生产，生产验收通知交给各任务负责人，验收通过后完成任务。

任务交付登记时固定用户评论版本。之后出现新评论时，发布暂停并由负责人核对用户最新决定；若范围不变且未要求暂停，负责人使用 `multica issue delivery review-project-comments` 提交当前 `revision`、`user_comments_version` 和具体 `scope_review`，不重设排队时间。需要修改或用户要求暂停时按实际要求处理，不能以该动作代替修改或解除暂停。

项目批次开始前，发布器核对当前 SQL 种子、int 数据库和发布占用；已清理的 int 按基线迁移重建结构、导入种子并绑定测试账号，再启动服务。成功发布后排空 int，确认没有未完成任务，停止属于 int 的进程并清理专属业务数据和上传目录；清理记录用于故障接续，下一批重新初始化。旧版单项交付若遇到已清理的 int，同样先恢复该环境。生产与 int 虽共用 PostgreSQL 实例，清理仅指向核对过的 int 数据库，不能停止共享实例或使用强制断开。未完成的任务、身份不符或恢复失败时保留现场和发布占用。

生产运行程序、产物和主分支核对一致后，发布器将 `multica-env/prod`、`multica-env/int`、`multica-env/verify-1`、`multica-env/verify-2`、`multica-env/verify-3` 作为远端环境基线原子快进至该提交，结果记录在 `.run/environment-baselines.json`。已有分支含未发布的独立提交、远端主分支变化或生产身份不一致时停止并保留发布占用，不能强制覆盖。基线引用不修改正在运行的 verify 任务工作树；槽位使用的实际程序版本以槽位部署记录和候选为准。

生产发布后，发布器从已验收产物归档和 SQL 样本建立该提交的种子，比较 SQL 与快照并在空闲槽位恢复验收，然后切换当前种子。维护器逐个更新空闲槽位的程序，验证后清空业务数据和上传目录；下一次领取任务前再导入当前种子。正在占用的槽位等任务结束后再更新；槽位原有启用状态及中断时的维护记录会保留。已完成维护的槽位若在同步期间再次领取并释放任务，其释放只清空数据并留下候选程序，因此空闲时按槽位部署提交和安装记录重新核对，不是基线就再次维护，不能凭历史完成记录略过。只有三个槽位同时空闲且都停在基线提交上才判定整次同步完成。迁移集合相同也会核对生产基线提交，确保实际程序跟随发布版本。验收中的任务以其槽位实际种子记录证据，不受当前种子切换影响。

迁移 686 和 691 只为交付批次及交付记录增加字段；690 原子放宽状态分类约束。旧程序在没有待发布任务时可使用既有状态，旧前端不具备待发布列；一旦出现待发布任务，不能把恢复旧程序视为完整回滚，须先核对这些任务和旧版界面的实际行为，禁止通过删除任务或直接修改迁移台账来恢复。

## 固定验收槽位

需要并行验收时使用专属 `verify-1`、`verify-2`、`verify-3` 三套环境；固定 `int` 仍是最终集成入口，`prod` 只接受经过 int 和用户发布授权的候选。验收槽位默认关闭，启用、排空和占用由现有交付记录及槽位接口驱动，候选历史按环境保留，verify 候选不能直接晋级生产。 独立 verify 候选从构建、部署到验收与中断续接固定源码和产物；其他任务推进主分支或生产版本，不使该候选失效。源码、分支、产物、实际运行身份及槽位租约与种子仍须一致。最终 int 整合与生产发布核对届时最新主分支和已发布基线，必要变化按影响补测。

槽位安装、重启核对和种子维护入口位于发布制品的 `operations/`，源码入口为 `scripts/verification-environments.py`、`scripts/verification-seed.py` 和 `scripts/verification-seed-copy.mjs`。槽位维护只允许重置专属验收数据库；int 由上述专用发布流程维护，prod 和事故留证库不属于测试数据清理范围。

### 种子生命周期

种子目录 `/data/cbs/multica-verification/seeds/<seed-id>/` 只增不改，`seed.dump` 与 `seed.json` 一一对应。`seed.json` 记录来源环境与采集提交、结构指纹（已应用迁移与实际表列摘要）、夹具版本与关键样本量、清理规则版本与校验和、构建与恢复验收的检查结果。种子编号发布后不可覆盖，失败版本不替换当前版本，旧版本保留可回退。

当前版本由 `.run/verification-seed.json` 指定，只由恢复验收通过的动作写入。未配置该指针时保持原有行为，不强制槽位恢复。

```bash
python3 scripts/verification-seed.py build  --id seed-<日期>-vN --from <已有种子目录> --release <候选产物目录> --postgres-config .run/verification-postgres.json
python3 scripts/verification-seed.py build --id seed-<日期>-vN --from-sql --release <候选产物目录> --postgres-config .run/verification-postgres.json
python3 scripts/verification-seed.py check-sql --seed <种子目录> --release <候选产物目录> --postgres-config .run/verification-postgres.json
python3 scripts/verification-seed.py verify --environment verify-1 --seed <seed-id> --postgres-config .run/verification-postgres.json --accept
python3 scripts/verification-seed.py ensure --environment verify-1 --postgres-config .run/verification-postgres.json
python3 scripts/verification-seed.py status
```

`--from-sql` 使用 `scripts/verification-fixtures.sql` 创建基础样本，账号密码与运行时绑定由目标槽位设置。构建生成快照和仅含数据的 SQL，并分别记录校验和。`check-sql` 在临时隔离库验证迁移身份、清理结果、全部表数据与序列值；通过后该种子的槽位恢复使用 SQL 导入，并沿用清理和关联校验。该检查不代表浏览器或真实 Agent 验收，也不更新当前种子指针。

槽位恢复时同时清空该槽位登记的上传目录；目录路径、属主和环境身份不符时停止恢复。任务代码目录和验收证据不属于上传目录。

`build` 在本轮新建的隔离构建库中按目标候选迁移建表，导入来源样本、执行清理、核对必需样本、序列、外键与结构指纹后写出新种子；构建库和导入库随后删除，不写 int 或 prod。`verify` 把种子装进指定槽位，在真实服务上核对登录、工作区、任务列表、Agent 列表及清理结果，全部通过后写入当前指针并把种子标记为已验证；任一项失败时槽位保持维护，当前版本不变。`ensure` 是发布器换任务前的门禁：槽位种子与当前版本不一致（或未标记已验证）时先按单槽位维护恢复，成功后才允许领取新候选。

清理规则集中在 `scripts/verification-scrub.json`，导入完成后在真实外键约束下执行，同时清空认证凭据、外部连接、租约、执行队列、自动化、监督、审查和上游同步状态。恢复流程按命名范围枚举执行型表并做覆盖自检：新增执行型表没有规则或显式豁免时直接失败并打印表名，不把新功能的自动执行状态带进下一个任务。

普通槽位恢复在停止程序或重建库前核对种子与目标制品的迁移内容身份，并校验迁移程序。当前槽位程序与种子迁移集合相同时直接恢复；前一任务增加了独立迁移时，外部维护器从种子 `build.release` 选取迁移身份相同的可信完整基线，校验全部清单及文件后复制到本槽空闲运行目录。排空并停止前一任务的全栈，在离线状态按基线建库、导入和清理；结构、样本及账号检查通过后才启动基线全栈并写入真实程序版本、目录和PID，随后由原pool正常部署下一任务并执行其原生增量迁移。不会先在未清理的前一任务数据库上启动基线Daemon。种子 `build.release` 的完整制品是恢复依赖，在该种子退役前保留。基线制品缺失、校验失败或出现未知消费者时保持该槽维护；停机、建库、账号绑定及启动阶段记录在槽位安装记录中，同目标重入先核对已记录进程归属。恢复后再核对实际结构指纹、必需样本和清理结果，通过后才登记已验证并恢复接单。没有结构身份的原始导出先执行 `build`。MCP 服务器的端点、headers/env 等凭据配置、Agent 绑定、待执行检查和 OAuth 状态都在种子清理范围内。结构不兼容或清理失败时仅该槽位保持维护；独立交付释放槽位或人工收回故障租约时将数据标为待恢复，下一个交付领取前按当前兼容种子恢复；同一候选持有原租约的续接不重置数据。

### 单槽位维护与换任务恢复

维护只调整目标槽位的接单开关，不移除环境池配置，不影响另外两个槽位和正在进行的验收。进入维护和退出维护都要求槽位空闲：维护结束后没有确认释放、或槽位已被领取时直接拒绝，避免把正在验收的槽位当成干净数据重置。

换任务时由发布器在领取槽位前按 `ensure` 核对数据版本及未使用状态，领取后再核对一次，不一致就隔离该槽位并等待外部恢复。仍持有原租约的同一候选暂停续接和重试不重置数据；已释放后重新领取属于新一轮独立验收，必须恢复。恢复后使用本槽位账号、认证密钥和 Daemon，种子中的历史交付标记为不再执行。

验收记录通过候选身份绑定种子：`validation_identity` 在 verify 环境包含环境、种子编号与校验和，因此同一程序在不同种子上的结果不算同一份证据；程序、结构或种子变化时按声明的覆盖映射补测或完整验收，未变化时复用原证据。

维护与种子登记通过控制端的槽位接口执行，默认控制端是 `prod`（队列真源）。演练可在隔离槽位充当控制端（`verification-seed.py ... --control verify-2`），生产配置仍用默认值；控制端只负责接口，被恢复的始终是指定槽位自己的数据库。

领取任务时，服务端把该任务当前的交付阶段、候选、被分配的验收环境、种子和所在批次写进领取载荷（`delivery_context`），daemon 每轮提示据此渲染 `## Delivery Context`：说明本阶段该做什么，并写明环境、种子和阶段由平台分配，Agent 不得自行换环境、重置数据或把单项验收当成已发布。

### 选择性组合发布

用户按任务逐个授权发布。发布器空闲时开一个收集窗口（默认 60 秒），把窗口内已验收且授权仍有效的交付冻结成一批（`delivery_batch`、`delivery_batch_member`，迁移 627–631），一项也照常发布。冻结后新批准的任务进入下一批，不改动已固定的成员和提交。批次成员关系不建外键：删除交付时在同事务内清理成员行和空批次；索引各自使用单条并发索引迁移，不在建表迁移里建普通索引。

- 批次候选以最新 `origin/personal-studio-upstream` 为基线按成员顺序合并各自固定提交，只构建并验收一个 int 候选，生产只切换这一份产物。
- 授权复核分两个时点：构建开始前失效的成员在合并前退出本批，候选按剩余成员重新构建；候选固定后失效的，已构建组合仍含撤权成员代码，整批停下并释放候选，剩余成员保留授权进入下一批重新构建和验收，不发布旧组合。
- 构建阶段进程退出时批次停在 `preparing`：重启的发布器接续同一批次（候选已部署直接进入验收，构建中断且 int 未切换则按原成员重来），构建异常整批结束并释放发布占用，不会永久卡在准备阶段。
- 合并冲突：冲突成员回到待修改，其余成员保留授权等待下一批。
- 组合构建、验收或发布真正失败：成员保留发布授权和既有证据，进入 `needs_changes` 等待修复或显式重试；释放本批占用，调度器不会自动重开同一失败组合。已批准的失败交付显式调用发布器 `advance` 的 `retry` 动作时，携带当前 `revision`、`worker_token` 和 `source_commit`，服务端检查后恢复排队。
- 发布成功把同一候选、同一提交和同一产物回填到每个成员并各发一次结果通知；重启、重复请求只回执状态，不产生第二次发布。
- 组合候选由本批代表交付在 int 上验收（登录、聊天、Agent 执行及成员相互影响）；成员依赖未批准的交付时暂停该组合并说明依赖。
- 组批默认关闭：只有 `.run/delivery-batch.json` 写入 `{"enabled": true, "controller_environment": "prod", "window_seconds": 60}`、服务端迁移 627–631 与控制器都已部署时才生效；未启用时沿用单项交付流程。启用前必须具备可用的已验证种子、单槽位维护和一次完整演练。


## 需求与开发

开发 Agent 依据当前指令与项目技能沟通：先查项目事实，澄清目标和边界，输出编号行动摘要及完整计划，用户确认一次后执行已授权动作。Multica 新任务从 `origin/personal-studio-upstream` 创建任务分支；已有任务续接原分支。保留其他任务的未提交内容。

续接已有任务先读取交付记录并复用当前方案；代码与方案没有变化时，不重发方案来引导确认。联调由 submit 后的平台队列准备，不先手动构建再补交付记录。

原任务评论保存方案全文，登记评论 ID 和 revision 后形成当前方案。自然语言授权由 Agent 结合任务上下文解释；平台核实引用评论的用户身份、任务归属和 revision，保存原文快照、范围解释和登记者，不匹配固定口令或评论层级。用户通过原任务评论沟通和确认；Agent 将真实决定登记到对应版本。

方案内容变化需重新登记；普通修复及未改变需求范围的主分支整合续接现有方案。Agent 根据用户最新决定判断是否仍在授权范围内，不通过重发相同方案要求再次确认。

CLI 与页面共用接口：

```bash
multica issue delivery plan GONG-24 --file /absolute/plan.json
multica issue delivery confirm-plan GONG-24 --file /absolute/confirmation.json
multica issue delivery revoke-release GONG-24 --file /absolute/revocation.json
multica issue delivery submit GONG-24 --file /absolute/delivery.json
multica issue delivery status GONG-24
multica issue delivery bind-checks GONG-24 --delivery <UUID> --file /absolute/required-checks.json
multica issue delivery accept GONG-24 --delivery <UUID> --file /absolute/evidence.json
```

- plan：`comment_id`、`revision`。
- confirmation：`plan_id`、`revision`、`comment_id`、`comment_revision`、`scope`。`scope` 是 Agent 对真实用户授权范围的解释。用户同时授权联调后发布时增加 `release_after_acceptance: true`；不要求评论晚于方案登记或处于特定线程。重复登记同一评论版本与类型必须使用相同解释。
- revoke-release：同样引用当前方案和用户撤销评论及 revision、`scope`；保留原授权及撤销依据，不删除历史。
- status：返回 `authorizations`（用户原话、类型、范围、登记者和撤销状态）、`user_comments_version`（当前用户评论版本摘要）及原交付记录。每条交付带 `authorization_state`：`user_authorization` 表示等待用户授权，`owner_review` 表示已落库待通知/待负责人核对，`review_incomplete` 表示通知已发出但复核尚未接续；其他阶段为空。
- delivery：固定 `operation_id`、完整 `source_commit`、`source_branch`、`base_commit` 和本地 `evidence`。证据是非空数组，每项含 `name`、`status: passed`、实际 `evidence`。重试保持操作号与内容一致。
- required_checks：新交付提交时必填，按已确认方案列出业务检查，保存到交付的 `plan_snapshot`，每项包含 `name` 与 `stage`（`verification` 独立功能验收、`integration` 最终组合验收），两个阶段各至少一项。六个协调检查名称不能充当业务检查。清单一经绑定不能删减或替换；范围变化使用新方案和交付。
- bind-checks：已有未发布交付缺清单时，负责人引用原 `plan_id`、当前 `revision` 和 `required_checks` 显式绑定，相同清单可幂等重试，无需用户重复授权。已发布历史不重开，失败交付不会因此自动重试。

```json
{"revision":3,"plan_id":"<当前方案UUID>","required_checks":[
  {"name":"真实模型与用量归属","stage":"verification"},
  {"name":"集成用量对账与页面","stage":"integration"}
]}
```

自动协调结果可以保留，但缺业务清单或必要项时 `acceptance_submitted` 为 false，平台通知负责人补验；不能靠六项协调结果晋级。`accept`、`approve`、发布器晋级和批次发布都核对业务项；组合代表的同一候选证据覆盖每个成员的集成清单。返回缺项时补真实检查，禁止把未执行事项改名标成通过。最终发布授权核对在 publishing 或已复核阶段也会拒绝缺项，并返回独立的 `business_error`，不把业务缺口解释成用户撤权。证据记录中保留每项实际来源，接口校验覆盖关系不能代替真实性审查。

- accept：当前交付 `revision`、准确 `candidate_id` 和实际业务验证的 `evidence`。存在发布授权时，同时提交 `authorization_id`、`scope_review`、`user_comments_version`，说明准确候选仍在授权范围内；缺少范围复核时只完成联调，不能自动发布。由按钮批准的候选复验使用 `authorization_id: "button"`，仅既有真实按钮批准允许复用。
- approve：验收后可引用新用户评论，提供 `comment_id`、`comment_revision`、`scope`、`scope_review`、`user_comments_version`；也可直接引用已有 `authorization_id` 并提供范围复核。任务身份不能无依据自批。

## 排队与源码恢复

发布操作包由候选中的 `scripts/delivery-operations.json` 声明。构建器在编译前核对所有文件存在且路径位于脚本目录内，制品携带同一清单，安装器按同一清单计算指纹并复制完整操作包。新增脚本只需维护候选清单，不能依赖当前旧发布器预先认识新增文件。缺文件时在构建前失败，不进入环境切换。

数据库的 `issue_delivery_plan`、`issue_delivery` 保存方案版本、固定提交、证据、用户批准和业务阶段。`.run/publish-requests/` 保存外部发布执行日志、结果及恢复资料，不能作为用户批准的替代来源。

外部 systemd 接力任务每15秒检查队列，不占 Agent 执行槽。固定 int/prod 的交付统一由生产控制端调度，同一任务通过交付归属令牌和代次隔离并发写入；相同方案、提交的重复登记返回原交付。正在验证的交付优先收尾，其余按创建顺序领取；int 被占用时保留排队状态，不 rerun、不重复 mention、不创建轮询自动化。接力单实例锁与现有 publisher/int/prod 锁共同串行化环境变更。

源码只从固定 Multica 仓库按完整提交恢复，建立 `refs/multica/deliveries/<UUID>`，在 `.run/delivery-sources/<UUID>` 创建干净工作区。原 Agent 任务目录不承担构建来源职责；运行结束可清理临时目录，分支和固定提交仍可续接。构建不携带 `.codebuddy`、`CODEBUDDY.md` 等运行时注入文件。

通过固定控制入口安装或恢复接力定时器：

```bash
pnpm --dir /data/ida/multica release delivery-worker --env int
pnpm --dir /data/ida/multica release delivery-worker --env prod
```

验收pool接力单元使用 `Type=exec`、`KillMode=process`：接力进程退出不结束跨任务运行的槽位服务。服务停启由canonical部署元数据中的PID、版本目录、环境身份和Daemon profile核对后执行；取消或中断后保留原租约/候选供接续，所有权不明确时隔离并等待恢复，不能用整组kill代替槽位清理。交付推进返回 409（执行已不是当前触发评论的最新运行，或阶段已变化）是围栏拦下的正常结果：保留原租约与候选、不回填失败，由最新执行结束后的常规路径决定交付去向；只有真正的异常才隔离槽位，兜底路径不能重做被拦下的写入。接力单元按交付和已安装控制器版本确定性命名，通过systemd核对ExecStart完整参数、工作目录、环境根、Type、KillMode和活动状态。任何版本的活动控制器都独占该交付；同版本inactive单元按原身份续启。旧版本inactive且MainPID已退出时，核对控制组剩余进程均属canonical槽位服务或其真实后代，再由新版本沿用原作业与租约接力，不停止槽位服务。身份异常明确记录该交付恢复受阻，其余交付继续调度；禁止随机单元名绕开并发约束。 接力单元显式使用实际执行用户 passwd 目录作为 `HOME`，恢复时核对相同值，使 Git 身份与 Go/包管理器缓存沿用同一账号配置。Git 整合只有实际未合并文件才归为代码冲突；身份、钩子等其它失败保留原始诊断，清理错误不能掩盖根因。

已提交准确候选验收证据时，接力直接处理接受结果，旧原生执行的终态不能覆盖已提交证据。有效外部验收归属期间不派原生验收；归属结束且无实际执行时补派一次，服务端固定通知标识负责持久幂等。被归属围栏延后的通知不算送达，等待循环不重复发送成功通知。

新运行产物携带同版本的发布操作脚本。发布入口验证服务后安装对应环境接力器；定时器是持久 systemd 单元，服务、发布器及机器重启后按数据库和日志继续。int 接力器禁止更新生产。配置、账号及环境地址取当前部署记录和私有 profile，不写入源码或日志。

## 联调与审核

联调源码必须是干净提交并包含已发布生产基线。复用固定 int，不建立额外预览；显式独立本地开发仍需要用户要求和 `MULTICA_LOCAL_DEV=1`。

接力器准备 int 后向原任务发送一次带交付编号、版本和入口的验收通知。负责人验证真实用户流程、关键组合、跨模块调用及持久化，提交简短测试清单和证据。接力器核对实际候选，执行原有 accept，释放 int，任务进入 `in_review`。

待审核代码留在任务分支，不提前合入主分支。其他任务可以使用 int；页面展示“已登记联调版本”，不把历史入口当作始终可访问的该任务版本。验证不足、冲突及运行异常有具体原因，不冒充通过。

## 用户确认与生产更新

用户可以在方案阶段授权“测试通过后直接发布”。授权先保存，Agent 验收准确候选并提交范围复核后，外部发布器完成验收并自动接续生产准备，不要求用户再次发送口令。只有执行授权时，联调后进入待审核，等待新的发布决定；方案、验收和发布决定均通过任务评论沟通，页面不另设交付确认卡片。

平台不会解释否定、疑问或 `/note` 的业务含义，由 Agent 提示词负责理解，不能将含糊表达登记为批准。平台拒绝不存在、被修改、其他任务、Agent 自己的评论及无权限用户的授权。发布前核对授权来源、当前方案、候选版本与已审查用户评论摘要；有新评论或来源变化时暂停发布并通过原任务通知负责人核对，通知可恢复且不会重复派发。

候选完成功能验收后按授权状态分流（验收可能发生在独立验收槽位 `verify-1`～`verify-3`，也可能发生在固定 int；复核通知只引用该候选自己的验收记录，不把独立验收写成最终 int 组合验收已通过）。授权已复核当前候选时直接推进发布；已有有效授权但未复核当前候选时，平台把待复核意图写入交付记录并定向通知当前负责人，负责人读取最新用户评论、候选提交和验收证据后，用 `approve` 提交 `authorization_id`、`scope_review` 和当前 `user_comments_version` 完成复核，范围未变时不再要求用户确认；没有有效授权、授权已撤销或范围不符时只记录等待原因，无人能自动批准。待复核意图按“交付 + 候选 + 源码提交 + 评论版本 + 授权记录”去重，通知号预先固定，重复轮询、重复回调和控制器重启都不会重复唤醒；负责人已有活动运行时保留意图等其结束后补发，通知失败同样保留意图由队列重试。复核已发出而负责人未接续时，队列在冷却期（10 分钟）后自动补发，最多 3 次；达到上限后保留原待复核意图和 `authorization_stalled` 标记，重复请求只返回同一失败原因、不再补发也不再重新计数，按原任务排查后手工接续。补发只在负责人没有活动运行时发起，同一候选不会并行叠两轮。早于该机制上线、已完成 int 验收且已有有效授权的历史交付，队列按同一条件补登记待复核意图后再通知；未登记通知前状态显示为待负责人核对（`owner_review`），不会显示成已通知未接续。上一轮验收运行仍持有交付归属时，先核对再 `recover-owner` 接续，不强行抢占。

批准后接力器领取全局最终发布占用，整合最新 `origin/personal-studio-upstream` 并固定基线。验收历史按验证输入保存；输入一致时复用，变化按声明的覆盖映射补测，未知影响、迁移或依赖变化执行完整相关验收。未改变需求范围时复用授权并复核新候选；范围或重要取舍变化返回用户确认。验证完成后快进合入、推送并核对远端主分支，再调用现有外部 publisher。最终占用覆盖整合、验收、推送和生产切换，所有发布入口共用占用。队列外主分支变化时保留候选并返回核对，禁止反复自动换基线或强推。

`release request` 与实际 publisher 都核对数据库中的批准、复核标记、原任务提交和候选身份。来源不符、批准失效或候选未包含批准提交时拒绝生产更新。

生产程序与 int 通过验收的程序相同，不重新编译。发布成功记录真实版本、日志及页面验收结果，生产验证通过后直接把任务标记为 `done`，不再等待用户二次确认；只到 int 联调验收、构建成功或部署启动成功都还不算完成，仍然进入 `in_review`；发布或验收失败保留当前状态并报告，不能关闭任务。未授权生产发布、未涉及发布的分析与配置类任务按各自完成条件收尾，本条不外延。

## 短暂维护与恢复

环境身份、数据库清理与生产数据保护遵守根 `CLAUDE.md` 的“环境身份与生产数据保护”，维护入口见 [环境维护](environment-maintenance.md)。程序发布授权不包含清空、重建或覆盖生产数据。

停止服务前核对进程归属、环境身份、数据库连接、源码及运行文件摘要。自动迁移仅支持新增表和并发索引：先在旧站运行时应用，再分别准备旧、新版本 SQL 查询。其他结构变更必须有单独的兼容与恢复方案，默认拒绝自动发布，旧站继续服务。程序恢复不能撤销数据库变更。

发布器建立持久化发布窗口并阻止本环境新认领。已有任务有120秒自然收尾时间，其后通过专用发布暂停信号中断，并最多等待60秒确认进程退出及检查点保存；提供商负责优雅退出及进程树终止，不强杀整个 Daemon。工作目录、未提交代码和会话保留，暂停不执行普通取消的自动提交及 worktree 删除。发布成功或旧版健康恢复后，按原执行建立唯一续接；人工取消、改派或自然结束的任务跳过。恢复先核对中断操作结果，不能盲目重复外部写入。窗口和恢复资料在数据库及私有 `.run/release-windows/` 记录，外部接力器重启后恢复。停止或保存未确认时不切换程序。首次升级旧 Daemon 仍使用旧协议排空，不假定其支持暂停。实际切换时由临时维护进程接管 Web 端口，显示维护提示并自动探测恢复；允许短暂连接中断，不承诺零停机。

生产窗口恢复负责人时，服务端把当时的交付编号、准确候选和窗口绑定到恢复执行。只有原执行确实承接该交付的集成或组合验收、窗口产物与候选提交一致、绑定时任务未完成，才合并后续发布收尾：恢复执行仍在排队或运行时，`published` 通知保持未投递，由持久队列重试，其他交付继续推进；恢复执行成功且任务在恢复后已完成时，以持久 `/note` 便签记录已完成的发布审计，不携带负责人提及或执行指令；创建、后续任务完成补派及评论重放均不唤醒。恢复失败、取消、任务未完成或候选不匹配时正常通知负责人收尾。普通任务与审查执行不视作发布收尾承接，不能仅凭任务已完成跳过通知。

新版本通过页面资源、登录、API、WebSocket、环境隔离及致命日志检查后才算成功。启动或业务验收失败恢复切换前程序与配置；恢复失败保留占用和恢复资料，停止后续发布。不得清库、重置生产数据或反复自动发布失败版本。

## 诊断、清理与构建标识

`pnpm release status`、`verify`、`verify-logs --env int|prod` 查看实际状态。源码以 Git 为准；运行目录各保留当前版本，切换期间临时保留旧副本，成功后删除。数据库、上传文件及任务工作目录独立于程序目录。

成功后清理本次构建工作区，确认提交已进入主分支再清理临时分支，不删除其他任务成果。清理失败单独记录，不回滚已验收生产。显式备份使用 `pnpm release backup`，数据库删除另行授权。

页面“构建 MM.DD-HH:mm”读取当前运行产物的 `built_at`，使用北京时间。晋级生产、重启及恢复旧产物保留原时间；悬停显示完整日期与源码提交。页面发现运行版本变化时提示刷新，不能把当前部署时间当成重新构建时间。

## 质量监督并发索引兼容性

迁移 550 创建 `(workspace_id, issue_id)` 的活动批次唯一索引，551 删除原工作区活动批次唯一索引。发布器仅接受这两份准确 SQL 的组合，其他非新增迁移仍拒绝自动执行。先创建成功再删除旧索引，均使用并发索引操作，不删除业务数据。旧程序仍通过工作区配置行锁和活动批次检查串行派发，且逐批收取结果，因此恢复旧程序无需撤销索引替换。恢复后将监督 Agent 并发设置回 1；等待既有批次结束，不清空阅读位置。只有确需回退数据库迁移时才在监督暂停、全部活动批次结束后执行 down，避免多个活动任务导致旧唯一索引创建失败。

## 运行代码差异

Daemon 在运行配置准备后采集任务目录基线，退出时在回收目录前采集结果。version=2 将任务目录、新检出仓库、关联外部 Git/非 Git 目录和已知技能目录分别展示为 roots；共享目录说明无法确定实际修改者，不把其他人的改动默认为本任务成果。扫描或读取不完整时明确展示缺口，不把未读路径视为删除。

运行前已有修改不计入本轮，运行中提交的内容仍计入；文件权限与软链接也属于修改。认证 CLI 下载的任务输入保存独立基线，纯下载不作为开发成果，随后对图片或附件的实际编辑仍显示。补丁在采集与服务端留存边界均脱敏。运行结果保存历史差异，查看不依赖原目录，也不从当前文件树回填旧记录。

评论、执行日志、执行实录和运行复盘共用历史差异。Web 每页最多50条轻量摘要，完整补丁按运行按需读取；未传分页参数的旧 CLI/监督工具保留完整运行身份集合，也不携带补丁。界面区分文件、目录、未确认归属和提示词修改。采集最多4个根，每根300个文件、单文件256KiB、每根补丁总计2MiB；超限标记部分结果。详情的文件树、补丁与平台文本修改各自保留可确认的证据边界。

## 快照与增量兼容

快照 `000_initial_schema` 的来源为 d91979d4c，覆盖至 496。快照模式执行 000 和 497 之后的增量；已有 000 台账时，历史范围按快照覆盖核对，不重放也不补造台账。升级前核对真实列、索引、约束及实际查询；ledger 条数不是缺失迁移数量。

564 仅补齐快照已有的 6 个应用列，使用 ADD COLUMN IF NOT EXISTS，不更新业务数据；565/566 补齐账号与执行轨迹的唯一索引。索引创建失败时停止验收并核查重复数据，禁止自动删行。程序回退保留这些兼容列和索引，旧程序可继续读取；迁移验证同时覆盖历史建库和快照建库。

测试数据库使用本次明确创建的隔离实例和库，记录目标、命令、提交、退出码及跳过项。生产及固定 int 的账号、Token、上传文件、工作目录不作测试夹具。每批同步的提交清单、报告覆盖及用户选择状态属于验收内容，不能只检查页面能打开。

`make test` 在执行迁移之前运行 `scripts/check-test-database.sh`，读取同一份 ENV_FILE，要求显式的 MULTICA_TEST_DATABASE_URL 与其指向同一目标，拒绝固定环境所在实例和本机冻结实例。测试目标须预先创建；该入口不会调用共享 Compose 准备脚本。检查同时核对 Make 实际导出的连接和 ENV_FILE 的连接，防止二者分歧。该检查不更改角色权限，也不能拦截任意 SQL。`cmd/server` 与 `internal/handler` 的 `TestMain` 在连接及清理 fixture 前复用同一检查器，缺少显式双变量、目标不一致或命中受保护实例时直接失败，不能回落到 localhost:5432。直接运行这两个包的 Go 测试同样需要两个变量；纯编译使用 `go test -c`，`-run` 过滤不跳过 `TestMain`。

## 交付归属与自动验收

CLI 写入交付时，Agent 的执行身份须等于服务端验证的当前 `MULTICA_TASK_ID`；缺少可信任务身份，或显式 `--execution` 与当前任务不一致时明确拒绝，不能伪装外部执行。工作区成员的外部验收使用稳定 `CODEX_THREAD_ID` 或显式 `--execution`，凭据保存在私有配置目录。`owner` 查询，`claim-owner` 领取，`recover-owner --recovery-evidence` 显式交接，`release-owner` 释放；旧代次不能覆盖新负责人。相同凭据的原执行可以续期，另一执行即使看到超时也必须提供恢复核对依据。

有效的外部验收归属租约由该执行者主动续期；平台保留候选及槽位，不重复派发 prepared 或 batch_ready 验收模型，也不因旁路原生验收执行结束而中断候选。外部身份由合法成员归属及不存在原生任务行的执行 ID 确认，不按名称前缀或旧阶段的 run 猜测。租约释放或过期后，持久通知恢复幂等投递；同阶段真实原生验收 run 结束且没有完整证据时按原协议失败。通知和终态失败写入在事务中复核归属、候选与准确 run，构建、迁移或部署故障仍正常失败。业务必验清单不因外部接管减项；未通过项保留缺口，结束外部验收时正常取消交付并释放归属。

候选可通过 `scripts/delivery-acceptance.json` 声明检查组、路径覆盖和参数数组命令，由 `run-delivery-acceptance.py` 在候选源码上执行。验收命令只访问 int/verify 环境，实际日志和不可变验收记录独立保存。声明只覆盖它真实验证的行为，真实 Agent 续接与生产浏览器结果仍需要对应证据。Agent 提交验收后结束本轮，外部发布器通知下一阶段，禁止同步等待自身执行进程被更新。

联调时核对：迁移在隔离实例完整执行，`done` 任务建立轮次并派发真实模型批次，未完成任务不派发，重开后迟到结果只归档，完成后的评论不进入本轮范围，页面显示轮次序号、截止时间和本轮覆盖。

组合候选就绪时，所有成员通过持久 `batch_ready` 通知获得同一候选和代表交付编号；代表按全部成员影响与集成冒烟汇总真实证据，通过 `multica issue delivery accept <issue> --delivery <代表交付> --file <JSON>` 提交。JSON 包含当前 `revision`、准确 `candidate_id` 与 `evidence`；同候选、同证据重放不重复记账，旧候选和非代表提交被拒绝。单项历史证据与平台通用检查不能替代本次组合业务验收。成员撤权时旧组合整体丢弃，剩余有效成员由新批次重新领取并构建；未批准任务不进入候选。

批次验收同时核对成员交付和本地候选：成员已取消或已发布、候选已释放时，通过正常 `abort` 结束失效批次，再调度有效成员；取消一条交付不等于其批次已结束。批次重排、撤回与失败回填保留已取消、已发布交付的完整终态记录。冻结及晋级事务读取并锁定成员真实交付行；取消先提交则成员退出固定批次，候选固定后整批停止，其他有效成员正常重排；发布晋级先提交则沿用既有 publishing/published 禁止取消的规则。最后的发布回填只更新 publishing 成员；不合法前态保留完整交付行，成员记录为回填失败且不发送成功通知，批次准确记录物理产物已部署与回填异常，不代表能够撤销已经部署的代码。

### 交付耗时与阻塞诊断

按需运行 `multica issue delivery diagnose GONG-80 --limit 50`，或增加 `--delivery <UUID>` 固定一条交付。该命令只 GET 当前任务的交付诊断，不领取负责人、不延长租约、不唤醒 Agent，也不启动轮询。HTTP 入口为 `GET /api/issues/{id}/deliveries/diagnostics`，沿用任务可见性校验；返回内容不含发布令牌、轨迹正文或环境凭据。

- `summary`：当前阶段、确证的共享发布占用或验收槽位等待、负责人复核；同一批次的代表租约属于本批工作，不判成另一项阻塞。
- `events`：复用 `verification_event` 的槽位事件与 `delivery.*` 交付动作，包含事件间隔。交付动作与状态更新同事务提交，独立命名空间不参与槽位 FIFO 或原有执行状态展示。
- `phase_started_at/phase_elapsed_ms`：仅在有真实阶段变更事件时计算；旧记录缺证据时返回空。心跳、重复检查、同阶段动作不能重置阶段起点。批次内部直接回填的阶段与旧历史不保证有完整计时，不用 `updated_at` 冒充起点。
- `recent_issue_runs`：最近 10 次任务执行、实际重试血缘、等待原因、轨迹摘要与既有 usage。执行属于看板任务，不据此认定都运行了当前候选；用量字段分开列出，缺上报标记 `available=false`，缓存 token 不重复合计。

默认读取最新 1–200 个事件，并明确 `truncated_older_events`。后续按返回的 `next_cursor.since/after` 传入 `--since/--after` 增量读取；`has_more_newer_events=true` 时继续取页，正向分页不会跳过中间事件。`observed_retry_or_resume_events` 只统计本窗口已观察到的重试/续接，不是历史总次数。诊断没有确定阻塞时明确提示查看最近事件，不把等待直接判为故障。

构建在安装依赖或编译之前检查实际执行用户 HOME、Git/Go/Node/pnpm、Go 缓存写权限、锁文件与完整发布脚本依赖。整合源码前检查实际 Git 作者/提交者身份。结构化构建日志中的 `build_stage` 包括预检、安装依赖、Web、三个 Go 程序，分别记录完成或失败的 `elapsed_ms`；复用产物不会伪报一次新的编译耗时。

固定控制端还可运行 `pnpm --dir /data/ida/multica release preflight --source <checkout> --env int`。它只读输出当前执行器 UID/PID、Python、实际控制器/worker 文件摘要、与源码是否一致、工具路径/版本及当前运行源 `/healthz`。就绪为 503 时退出非零并标记 `blocked`，不写迁移台账。构建预检不强依赖另一个验收槽或正在切换的固定 int；候选迁移、真实运行身份、隔离和上线就绪仍由原生发布门禁验证。控制器与源码摘要不同只用于说明升级边界，不能据此跳过正式控制器更新或伪报同源。

出发的 maintenance-only 提交。`release maintenance-int --source <固定工作树>
--evidence <授权JSON>` 复用原构建、完整 operations 清单、发布窗口、锁和失败恢复，
保存普通候选及请求记录。它只允许控制恢复文件清单，不接受监督业务实现，且逐份
核对运行生产包与维护源码的迁移文件名及内容完全相同。

授权 JSON 包含 `base_commit`、`issue_id`、`comment_id`、`comment_revision`、
`comment_sha256`、`user_comments_version`、`scope` 和实际本地检查 `checks`。
评论必须仍是原任务用户评论的准确版本；出现新用户决定就暂停重新核对，不从文字
自动推导新授权。int 准备后进行真实控制端回归及浏览器验收，用既有 `accept`
登记准确候选，再用既有 `request` 交给外部发布器。维护 worker 等来源执行完成后
才更新 prod，不占 Agent 执行槽等待自身重启。

维护不会修改交付的生产批准。队列和 publisher 锁、现场 PID/profile/连接、完整
制品指纹和源码范围在切换前重新核对；其他交付或活动任务存在时拒绝切换。
维护排空上限 90 秒，不进入 120 秒后的任务暂停步骤。安装完整带指纹 operations
包，失败沿原恢复路径回旧程序，保留数据库、队列和原隔离记录。控制端维护成功
不代表业务候选已上线，原任务仍须通过自己的 verify/int 验收。

### 外部发布器 Git 认证与失败恢复

发布器以 systemd 实际 User 的 HOME 读取该账号既有受控 Git 凭据。root 控制端当前使用 `/root/.config/gh/hosts.yml` 的已授权 GitHub CLI 账号，由 `gh auth setup-git --hostname github.com` 配置 credential helper；不复制模型运行环境中的临时令牌、不把凭据写进 remote URL、Git 参数或仓库。凭据文件限制为账号本人可读；失效后由来源维护方重新授权。发布前在相同 systemd User/HOME、清除临时 GH_TOKEN/GITHUB_TOKEN/GIT_ASKPASS 的环境执行 `git push --dry-run`，随后 fetch 核对基线；dry-run 成功不代表已发布。

失败维护请求显式恢复时，`maintenance-int --source ... --evidence ...` 的授权证据可携带原 `retry_request_id`；入口核对同一任务、原基线、failed 状态与无活动发布器，沿用原请求编号准备新的固定候选。新候选重新验收和 accept 后执行 `retry-request <原编号>`。普通 request 不自动恢复失败；同编号 queued/publishing/succeeded 重放不会再启动发布器。历史失败尝试保存在 previous_attempts，归档按提交隔离，不覆盖旧验收产物。恢复不得绕过新用户评论复核、维护文件边界或迁移身份检查。

请求记录保存 failure_stage、脱敏 error、log_path 和 journal_unit。子进程输出进入同一脱敏请求日志；原始 journal 可用 `journalctl -u <journal_unit>` 定位，仅由受控运维读取，不上传认证文件。发布器未运行时不启动第二套常驻 worker，显式恢复仍使用原单请求 systemd 执行入口。

### 无生产授权的固定 int 验收

未批准交付在 verification 已提交且声明 integration 必验项时，控制端队列返回
`integration_pending=true`。既有外部 worker 用当前 revision 调用 `claim-integration`，
服务端锁定交付并复核方案和 verification 证据，再进入 `preparing_release`，在原快照
标记 `integration_only`。此动作不写生产批准。原 verify 证据保留在 delivery_evidence，
清空当前候选与 acceptance_submitted；新 int 候选经既有 int-prod 租约、固定基线整合、
构建、prepared 和通知流程准备。环境池继续服务其他任务。

负责人仍使用 `delivery accept` 提交当前准确 int 候选的 integration 业务证据。
worker 的 `integrated` 动作校验候选、revision、worker token、publication generation
与有效租约，成功后记录 integration_complete、进入 awaiting_review 和 in_review，
释放 int 候选及占用。重复领取或过期回调被拒绝；中断沿原 publication 恢复路径续接，
失败保留 needs_changes，不算完成。生产 validated/publishing 仍独立检查发布授权，
仅集成验收不能更新生产。后续获批准仍由原发布路径准备并复核准确候选。
### 修复审计请求与 operations 单独更新

`slots/advance` 的请求上限保持 8192 字节。repair 在本地比较完整制品清单与实际
全量 SHA-256 后，发送 source/candidate 身份、受控制品及 manifest 引用、文件数量、
清单摘要、旧版本和兼容报告引用/摘要。清单摘要口径为 Python JSON 的

摘要只用于审计，不代替全量校验。兼容说明全文保存在制品目录旁的受控 sidecar，

字节数，超限不调用接口。原失败记录和 owner/lease/source/seed 围栏保持。

仅 operations 维护且已有明确授权时，可使用现有 `issue-delivery-worker.py --install`
完整包安装器：从固定提交的 `scripts/delivery-operations.json` 提取全部文件（包括
清单本身），置于控制目录 `.run/publisher/` 的独立输入目录，核对完整清单与源码
字节后，以 `MULTICA_RELEASE_ROOT=/data/ida/multica` 调用该输入目录 worker 的
`--env int --install`；受控接口验收通过后对 prod 消费者同样安装。

安装器按整个清单计算指纹并安装独立版本目录。核对 systemd ExecStart、每个文件
SHA-256 和后续实际 worker 入口；保留旧包及回退入口。不逐文件修改运行包，
不更新业务程序、迁移或生产配置。包含控制端程序修改时仍走 maintenance-int。

字节响应的脱敏文本、接口路径、失败阶段、日志路径及 journal unit；不记录请求
正文或 Authorization。保留 HTTPError 类型与可读错误体，409 围栏处理继续有效。

维护候选必须包含当时远端维护主线，发布前 fetch 后校验祖先关系并仅快进推送。生产版本可以落后于已合入的维护提交；生产基线仍单独核对，不能覆盖后来推进的主线。

## GONG-78 审查、证据和外部执行

所有任务均参与自动审查判断，不按任务类型排除。`no_action` 表示本轮没有待处理交付，不写通过标记、不改变任务状态、不唤醒开发。需求正文、真实用户决定或固定候选发生变化后重新判断；解释性 Agent 回复及平台通知不构成新候选。首轮核对完整需求和决定，后续优先读取变化及上一轮问题，必要时回读原文。

代码审查绑定关联 PR 或已验收交付的固定提交。Daemon 在启动模型前准备并核对该提交，缺少唯一仓库、目录不可用或提交不符时不启动代码审查。没有代码候选的轮次只判断交付材料，不读取无关目录最新提交。审查员不能作为普通委派协调者被完成事件唤醒。

差异协议 version=2 已覆盖任务目录、运行中新检出的仓库、关联外部 Git/非 Git 目录及本任务已知技能目录。共享目录明确标注无法确定修改者；扫描不完整时不将未读路径视为删除。文件权限和软链接作为独立修改记录。认证 CLI 下载附件时保存输入基线，纯下载不显示为开发成果；随后修改图片、附件或新增业务文件仍显示。历史快照不会用当前文件树回填。

管理入口读取只返回布尔值的工作区能力接口；无权限返回200/false，实际管理接口继续严格校验权限。

运行列表每页最多50条摘要，完整补丁按运行按需读取；工作区其他任务事件不会使当前议题运行历史全部失效。执行日志展示时间戳可确认的排队、准备和执行区间，执行时间包含模型与工具，不将重叠运行之和称为任务墙钟时间。构建和验收沿用既有输入身份，输入未变时复用；结构、依赖或未知影响仍执行完整相关检查。

完成轮次在事务内将原文、代次和阅读位置冻结到 `supervision_frozen_material`，尚未派发时编辑或删除原评论不会改变本轮材料。新材料属于后续轮次或人工检查。既有批次仍读取自身已固定的证据。升级前已覆盖的原文无法可靠重建，不补造完成快照。

650 扩展审查状态约束，653 追加默认空串的输入版本；发布入口只接受两份准确 SQL 的已审查摘要。651 新建原文表，652 用独立并发索引迁移约束身份。旧程序可忽略新增表列，回退保留扩展约束和证据，不执行 down、不清理业务行。恢复旧程序前停用自动审查，避免旧版本将 `no_action` 当作新轮次处理；已运行审查按现有排空流程结束。

历史证据维护入口为 `go run ./cmd/repair-run-evidence --workspace <UUID>`（在 server 目录，显式设置 DATABASE_URL）。默认只读盘点，仅输出身份和摘要，不输出原文或敏感值。完成目标核对及备份后，以盘点输出的 `--apply-inventory <SHA256>` 精确应用；清单变化时拒绝写入。只清洗明确敏感补丁及有 delivery_notice 来源、且未被授权记录引用的平台通知；未知文件归属和丢失原文不重建。程序修复、历史处置和线上业务验收分别记录。
### 独立验收后批准生产

固定 int 保存当前候选的 integration 证据，原 verification 证据保存在同一交付的历史记录。当前 int 已完成且证据完整时，批准入口可复用同交付、同源码的完整 verification 记录；不能拼接不同候选的部分检查，也不能使用其他交付或其他源码的记录。缺少任一阶段证据仍拒绝批准。回归必须覆盖 verification→仅 int→用户批准生产的完整转换，不能仅测试到 in_review。

### 常规交付的时间目标与恢复

常规、范围明确且已获必要授权的任务以30分钟全流程为目标，记录从确认执行到正确交付的真实墙钟时间；排队、构建、模型、工具、审查、发布和人工等待分别记录，不能靠排除失败或等待声称达标。复杂需求或外部依赖超时不承诺固定完成时间。

提交前一次核对账号、模型真实runtime、凭据来源、环境/候选字段及所需工具，先跑一个最小真实样本，再做矩阵。初始化种子会清理临时配置，使用受控prepare入口恢复并在结束时还原；int按真实数据库、进程和publication租约核对，不能套用verify的slot/seed字段。

当前候选与旧样本的业务实现、规则技能及配置逐项相同，且保留准确版本和SHA256映射时，复用未变化的真实证据；新增风险只做针对性复验。纯验收/控制工具独立固定提交，不因此反复重建业务程序。准备失败先修普通前置条件，不将其误报为业务失败；恢复沿原交付或合法串行新attempt，不并发重复启动。

已授权控制维护在既有候选记录登记占用，已有执行继续，新验收和集成排队；真实publication或运行任务仍阻止切换。fenced旧记录只有在没有候选、归属、槽位和接力进程时才不算活动占用。维护结束使用其固定完整operations包，避免程序制品旧快照覆盖新工具。暂缓新队列轮询只能停止timer，不能把verification-pool.enabled当准入暂停开关，该开关还决定verify/串行int路由。所有临时暂停均记录原状态并恢复。

每次接续只交接当前阶段、准确候选、尚缺检查、适用证据、工具版本、失败点及下一动作；不重新展开整个任务。验收轮次退出用于交还发布器，不等于原任务已完成；已授权普通修复继续至真实验收收尾。完整回归覆盖verify→int→审查→批准→发布→恢复，不能只验证到in_review。

用户明确由外部执行者接管时，复用原任务和归属租约，不另派开发任务。有效外部归属持有期间，组合验收及发布完成通知等待其收尾；任务在准确交付发布之后标记完成，通知只保存免触发审计。历史done不能证明新候选已验收，租约释放或过期且尚未收尾时恢复既有通知兜底。

## OpenViking 专项验收

生产长期启用，int、verify 和本地开发默认关闭；长期边界见 CLAUDE.md。本节只说明现有环境配置和启动检查的操作方式，不改变环境发布流程。

### 普通测试与种子恢复

`.run/env/<环境>-services.json` 是固定环境配置真源，Server 和 Daemon 的 `MULTICA_OPENVIKING_ENABLED` 均为 `false`。普通测试不需要 OpenViking 服务、资料索引或记忆提取完成；保留的历史待同步记录不重放。关闭状态下知识库原生代理拒绝请求，不能凭残留 URL 访问生产。现有进程启动器同时移除 OpenViking 凭据和真实目标，并为关闭进程注入不可连接的回环零端口，阻断旧知识库客户端回退到本机生产默认端口；配置真源仍只保存关闭开关。

验收槽位初始化显式写入关闭值。本地 `.env.example`、工作树环境生成和开发入口默认关闭，并清除宿主继承的 OpenViking 配置。构建不携带运行连接；发布从目标环境配置启动，不从生产复制测试接入。种子清理 `openviking_event`，连接中显式关闭采集；不复制原生数据、归档目录或专项开关。此规则用于后续种子恢复，不授权清理当前留存数据。

### 临时启用

1. 确认是 OpenViking 专项验收并核对当前环境空闲。保留原配置及部署记录，选定本机独立端口和已存在的独立数据、归档目录；不得重用、嵌套或绑定挂载生产目录。
2. 原生配置的 `storage.workspace` 指向专项数据目录，`storage.agfs` 和 `storage.vectordb` 均为 `{ "backend": "local" }`；原生进程只绑定本机，并以 `openviking-server --config <配置绝对路径>` 启动。模型服务可复用；模型服务不等于 OpenViking 的数据或向量存储。
3. 生产环境配置中的 `MULTICA_OPENVIKING_CONFIG_FILE` 指向实际原生配置。现有环境控制器从生产真源生成部署记录的 `openviking` 非敏感身份，包含实例地址、数据目录和归档目录；核对运行进程后登记。记录不含模型或认证凭据。登记时复用现有控制器：先执行 `r.check_live_environment("prod", metadata, config)`，再将 `r.openviking_identity(config)` 写入该生产部署记录的 `openviking` 字段；字段待核对或缺失时专项启动会拒绝。
4. 在目标环境 Server 与 Daemon 的现有配置中同时设置下列变量，地址和目录改成该环境的实际值：

```dotenv
MULTICA_OPENVIKING_ENABLED=true
MULTICA_OPENVIKING_ACCEPTANCE=true
MULTICA_OPENVIKING_URL=http://127.0.0.1:19446
MULTICA_OPENVIKING_CONFIG_FILE=/absolute/isolated/ov.conf
MULTICA_OPENVIKING_ARCHIVE_ROOT=/absolute/isolated/archive
MULTICA_OPENVIKING_PRODUCTION_DEPLOYMENT=/data/ida/multica/.run/deployments/goal-test-prod.json
```

5. 用候选 `server/bin/multica config check-openviking` 在目标 Server 配置环境执行只读检查，再通过现有启动入口重启目标 Server/Daemon。控制器和两个进程共用同一校验器；校验前不向 OpenViking 发请求。它核对显式专项声明、实际生产部署记录、本机端口、原生进程的 `--config`、本地存储及真实目录，拒绝生产端口别名、目录重叠、符号链接/绑定挂载共享和无法核对的配置。当前只支持可核对的本机 Linux 原生进程与本地存储；未知远端、容器或外部存储会拒绝，不能只声明“已隔离”。
6. 专项请求只能进入该独立实例。以实际原始日志、附件哈希、记忆提取和后续召回验证功能；保留实例、路径、源码与证据的对应关系。

1. 记录专项验收证据，等待正在执行的任务结束，使用现有 Daemon 排空入口停止新认领；不清理数据库或归档。

3. 验证普通聊天和任务、DSH/Codex、系统角色及原有 Skill 链路可运行；数据库采集计数、保留归档目录不因普通任务增长，原生 API 代理关闭。生产仍启用并在不可用时暂停新任务。
