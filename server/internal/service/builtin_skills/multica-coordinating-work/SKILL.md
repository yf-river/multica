# 持续协调与交付

Mika 或受托协调者负责安排、判断依赖、处理异常和核实结果；开发负责人编写代码，项目既有发布器控制共享环境。不要为协调再造发布器，也不要替开发者重复实现。

## 接手与安排

1. 从当前任务清单确认本次范围。读取原任务的最新决定、负责人、活动执行、分支、交付和完成条件；项目只是背景，不能代替授权。已完成任务复用其证据，不重新接管。
2. 在协调任务中记录简短清单：任务、目标、负责人、依赖、准确候选、已有证据、授权与停止条件、下一步及唤醒来源。每次只更新发生变化的项，任务和交付记录仍是真源。
3. 独立开发和验收可以并行；共享 int、生产和发布工具升级由唯一现有发布入口串行。公共链路有问题时先用最小真实案例恢复它，不把更多任务塞进同一个故障点。
4. 根据任务的真实代码仓库读取对应规则和技能。Multica 开发交付遵循 `multica-working-on-issues` 与目标仓库发布文档；其他项目不能套用 Multica 的环境和状态约定。

## 跟进与恢复

- 优先读状态摘要、最近结果和增量事件。新结果、失败或依赖解除时接续协调；派发后保存可恢复的记录并结束本轮，不用持续占用模型等待。
- 唤醒前核对现有 active/queued 与派发回执。普通评论仅记录，不代表正在执行的 Agent 已读。确需纠正当前执行时先核实实际进展、检查点和安全终止边界，再通过正常入口续接一次。
- 同一等待连续三分钟没有实质进展，先检查一个明确问题：正在等哪个执行/资源、租约是否有效、最新业务动作是什么、是否已有结果。没有新证据不反复读全量日志。
- 时间长不等于卡死。有效工作继续；已过期、已终止、错误权限、错误测试入口或无法满足的前置条件应转为具体阻塞。根因未变不重复登记、重试或增加超时。
- 一项异常只阻塞真实依赖它的任务。保留候选、源码、证据、操作幂等键和最后外部结果；未知写入结果先对账，不盲目重放。
- 审查或系统反馈唤醒你、链顶没有人类发起人时，仍可在成员已授权的当前任务范围内继续委托同一个私有开发 Agent；该继承只覆盖这条任务及其直接子任务和这个 Agent，任务结束即失效，不推出其他任务、其他 Agent 或新顶层任务的权限（判定与拒绝原因见仓库文档 `docs/operations/agent-invocation-authority.md`）。

遇到发布、验收和模型执行异常，按需读取 [故障处理案例](references/failure-patterns.md)。接续协调的事件与恢复入口见 [协调能力边界](references/coordination-source-map.md)。

## 验收与收尾

- 建立最小完整真实案例：先验证前置条件和入口，再验证用户行为、持久化及必要权限。长执行的续租/取消用受控短租约测试，真实模型验证小批完整链路；不能只跑小批就宣称长任务可靠。
- 脚本必须保留真实退出码。跳过、无测试对象、仅页面可打开或仅派发成功都不能记为业务通过。验收项未通过时留下缺口，不能用解释文字抵消 passed 标记。
- 未变源码与产物复用原证据；有变化按影响补测。独立验收期间其他任务上线，不应主动重建该候选；最终组合必须验证成员间影响及集成冒烟。
- 发布器自身升级要验证实际执行器和旧新版交接，不只检查待发布制品。生产完成要核对实际版本、就绪、真实业务与原任务停止条件，再收尾；审查通过不是生产成功。
- 报告阶段耗时、失败尝试和可取得的 token 用量。并行耗时不相加，缓存 token 不当作新增输入重复计算，缺少数据明确标注。汇报只写结果、阻塞、下一步和需要用户决定的事项。
- 新的业务取舍、权限或破坏性影响交用户决定；已授权的常规推进自行完成。清理前确认分支已合入、工作区干净、没有执行者使用，证据与恢复材料另行保留。
